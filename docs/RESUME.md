## 二、面试 8 问 8 答

### Q1：为什么选 LanceDB / Chroma，而不是 Elasticsearch？

**答**：
- **场景**：这是单机、Windows 开发环境的个人项目，数据量 19 份文档（chunk 数百级），远未到需要 ES 的量级。
- **成本**：ES 需要 Java 运行时 + 常驻服务 + 较大内存占用，Windows 上部署易翻车、维护成本高；LanceDB / Chroma 是嵌入式、磁盘持久化、无独立服务进程，`pip` 装完即用。
- **能力够用**：向量检索 + 元数据过滤（Chroma）+ 列式存储 + 全文检索（LanceDB）已覆盖本项目需求；BM25 我用纯 Python 自实现（char-bigram 分词），不依赖 ES 的倒排索引。
- **选型对比本身就是面试素材**：InMemory（零持久化）vs LanceDB（列式、可嵌入、支持 FTS）vs Chroma（向量检索成熟、简单）vs ES（分布式、运维重）。结论：**个人项目优先嵌入式方案，规模上到千万级文档/多节点再上 ES**。

### Q2：BM25 与向量检索各自什么情况下失效？

**答**：
- **BM25 失效**：① 纯词法匹配，无法理解同义/近义（"降级运行" vs "降级模式"匹配不到）；② 中文需分词，词表外词/专业缩写（如 CBTC、ATP）若切词不当会漏检；③ 对长文档的语义相关性判断弱。
- **向量检索失效**：① 精确关键词/条款号/编号（"第三十五条"、"1500V"）这类精确匹配，语义模型可能泛化到不相关片段；② 罕见专有名词的 embedding 表征不稳定；③ 数值区间/范围查询不擅长。
- **互补性**：所以用 **RRF 融合**两者——BM25 兜住精确关键词，向量兜住语义相似，融合后 recall@5 从纯向量的 98.4% 提到 100%。

### Q3：RRF 与加权融合的区别？为什么选 RRF？

**答**：
- **加权融合**：`score = α·norm(向量分) + (1-α)·norm(BM25分)`，需要先做**分数归一化**，但 BM25 分与余弦相似度的分布差异极大、量纲不同，归一化策略（min-max/z-score）对结果敏感，α 也要调参。
- **RRF（Reciprocal Rank Fusion）**：`score(d) = Σ 1/(k + rank_i(d))`，**只关心排名不关心分数绝对值**，天然规避量纲问题，无需归一化，k（默认 60）鲁棒性高。
- **选 RRF 的理由**：实现简单、无调参负担、对不同打分器更稳健。我的实现里保留了 `alpha` 加权路径（可配置消融），但默认走 RRF。

### Q4：bge-reranker 的推理开销如何权衡？

**答**：
- **开销来源**：bge-reranker-base 是 CrossEncoder，对 `(query, doc)` 成对做交叉编码，**计算量随候选数线性增长**，且比双塔（bi-encoder）慢一个量级。
- **权衡策略**：**两阶段**——第一阶段用向量+BM25 召回 Top-K（K 取 5，候选数 10，因为融合要 top_k*2），第二阶段只对少数候选做重排，而不是全库交叉编码。
- **实测**：检索延迟从 35.3ms（纯混合）涨到 3.77s（加重排），**以 ~3.7s 延迟换 MRR@5 0.926→0.955**。这是典型的**精度换延迟**，生产上可按请求重要性动态开关（我的 `use_rerank` 开关已支持）。
- **结论**：召回→重排两阶段是业界标准做法，关键是把重排的输入控制在少量候选（10~50 级），而非全库。

### Q5：context_recall 低说明什么？

**答**：
- **定义**：标准答案所需的信息，有多少被检索进了上下文。低 = **"该召回的内容没召回"**，是**检索层的召回问题**，与生成无关。
- **我的数据**：A/B/C 三方案 context_recall 为 0.765 / 0.756 / 0.854，方案 C（查询改写）最高 0.854，说明**改写查询能显著提升召回**。
- **排查路径**：① 先看是不是 chunk 切分不合理（关键条款被切断）；② 看 embedding 模型对专业语料表征能力；③ 看多跳题（23 条 multi_hop）是否因为单次检索拿不全跨文档证据——这正是 GraphRAG/多查询增强的价值点。

### Q6：缓存一致性如何处理？

**答**：
- **我的方案**：双层缓存（embedding + LLM），键都是**内容的 hash**。
  - Embedding 缓存：键 = `sha256(文本)`，文本不变则 embedding 不变，天然一致。
  - LLM 缓存：键 = `sha256(messages 序列化)`，问题+检索上下文全变则 miss。
- **一致性风险**：若**知识库更新**（重新入库、chunk 变化），旧的 LLM 缓存仍会命中旧答案。处理：① 缓存带 TTL（LLM 默认 3600s）；② 入库时可按索引版本清空缓存；③ 生产上更严谨的做法是缓存键里纳入"文档版本号"。
- **对个人项目**：TTL + 可清空的磁盘缓存已足够，我在报告里也写明了这一限制。

### Q7：GraphRAG 的代价是什么？

**答**：
- **收益**：解决多跳/全局性问题（"信号维修五级 vs 轨道维修四级"这类跨文档推理），通过实体+关系抽取构建知识图谱，跨 chunk 关联。
- **代价**：① **构建成本**——需对全库做实体/关系/社区摘要抽取，LLM 调用量大、耗时长、token 成本高；② **存储成本**——图谱额外占用磁盘；③ **查询延迟**——图谱检索 + 原图检索两路，链路更长；④ **复杂度**——图构建/更新/索引的工程复杂度显著高于向量检索。
- **我的处理**：因 GraphRAG 管线未跑通，方案 C 降级为**查询改写**（更轻量、零构建成本），并在报告里如实说明。面试时主动讲"为什么没硬上 GraphRAG"反而是加分项——体现了成本意识。

### Q8：100 条评测集如何保证标注质量？

**答**：
- **原则**：ground_truth **禁止 LLM 凭空生成**，必须可回溯到原文。
- **做法**：① 逐条**手工从 19 份语料原文抽取**，条款号（第三十四~三十七条、第九~十五条）、检修周期数值、限速值、事件分级阈值等均为原文真实内容；② 每条带 `source_file`（精确到文件）+ `source_page`（定位到段落），**可回溯**；③ 类型分布按指令约束（multi_hop≥20 / table≥10 / numeric≥10），多跳题专门设计跨文档推理。
- **最终 125 条**（超 60 条要求），类型：single_hop 65 / numeric 26 / table 11 / multi_hop 23。
- **诚实**：我明确在报告里写"ground_truth 由执行者手工抽取，未用 LLM 生成"，这是标注质量的核心保证。
